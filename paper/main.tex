\begin{abstract}
Fine-tuning image models in PyTorch repeatedly requires the same scaffolding:
data loading, augmentation, a mixed-precision training loop, checkpoint
selection, metric tracking, distributed handling, and an export path. Writing
this by hand is verbose and error-prone, while heavier frameworks trade
boilerplate for their own abstractions and are oriented mainly toward
classification. We present \textbf{FujiCV}, an open-source library that provides
a single, config-light \texttt{ModelBuilder}\,$\rightarrow$\,\texttt{Trainer}
pipeline spanning classification, regression, multi-label, and
metric-learning/retrieval on top of the \texttt{timm}, \texttt{torchvision}, and
Hugging~Face model zoos. FujiCV includes modern training techniques (EMA, SWA,
SAM, Model Soups, Mixup/CutMix, LLRD, gradient accumulation, DDP,
\texttt{torch.compile}), explainability (Grad-CAM), hyperparameter optimization,
retrieval (ArcFace/CosFace/GeM), and deployment (ONNX, TorchScript, post-training
quantization) out of the box. We show that FujiCV substantially reduces the code
required for a complete training pipeline while adding negligible throughput and
memory overhead relative to an equivalent hand-written PyTorch loop, and that the
abstraction preserves accuracy across standard benchmarks. FujiCV is released
under the Apache-2.0 license and is available on PyPI and GitHub.
\end{abstract}

\textbf{Keywords:} deep learning; computer vision; image classification; transfer
learning; PyTorch; open-source software

\begin{enumerate}
  \item A unified, config-light API covering \emph{classification, regression,
  multi-label, and retrieval} in one interface on top of \texttt{timm},
  \texttt{torchvision}, and Hugging~Face backbones.
  \item Modern training, explainability, retrieval, and deployment techniques
  available out of the box with minimal code.
  \item An empirical study showing substantial boilerplate reduction at
  negligible compute overhead and no accuracy loss.
  \item An extensively tested, continuously integrated, reproducible
  open-source release.
\end{enumerate}

\section{Design and Architecture}
\label{sec:design}
% Figure: pipeline diagram ModelBuilder -> Trainer -> eval/export.
% Philosophy: plain Python constructors, no hidden global config; every knob is
% a keyword argument; resolved config (with package+git version) saved per run.

\begin{lstlisting}[language=Python, caption={A complete CIFAR-10 pipeline in FujiCV.}, label={lst:quickstart}]
from torch.utils.data import DataLoader
import torch
from fujicv.data.datasets import get_default_dataset
from fujicv.data.transforms import get_train_transforms, get_val_transforms
from fujicv.engine.trainer import Trainer
from fujicv.losses.classification import CrossEntropyLoss
from fujicv.metrics.classification import Accuracy
from fujicv.models.builder import ModelBuilder

train_ds, val_ds, c2i = get_default_dataset(
    "cifar10", root="data",
    train_transform=get_train_transforms(32), val_transform=get_val_transforms(32))
train_loader = DataLoader(train_ds, batch_size=128, shuffle=True,  num_workers=2)
val_loader   = DataLoader(val_ds,   batch_size=128, shuffle=False, num_workers=2)

model = ModelBuilder("resnet18", task="classification", num_outputs=10,
                     image_size=32).build()
trainer = Trainer(model=model, train_loader=train_loader, val_loader=val_loader,
                  loss_fn=CrossEntropyLoss(), metrics={"accuracy": Accuracy()},
                  optimizer=torch.optim.AdamW(model.parameters(), lr=1e-3),
                  epochs=10, task="classification", output_dir="runs/cifar10",
                  monitor_metric="val_accuracy")
history = trainer.train()   # -> best.pt  last.pt  history.csv  history.json
\end{lstlisting}

\subsection{E3: Accuracy parity}
\label{sec:e3}
To confirm the abstraction does not cost accuracy, we train the \emph{identical}
recipe --- the same torchvision ResNet-18 from scratch, $32{\times}32$, five
epochs, AdamW at $3{\times}10^{-4}$ with cosine annealing, AMP, resize+horizontal-flip
augmentation, and plain-resize validation --- with a hand-written loop and with
FujiCV, and compare top-1 CIFAR-10 accuracy (Table~\ref{tab:accuracy}). Reaching a
valid comparison required removing three confounds that each produced a spurious
gap: a stronger default augmentation preset ($66.2\%$), a different backbone
implementation (timm vs.\ torchvision, $67.9\%$), and FujiCV's default
resize-then-center-crop validation transform, which mildly degrades
native-resolution evaluation. With all three equalized the two agree to within
run-to-run variance ($\Delta = +1.0$~pt). This underscores a general point
(\S\ref{sec:threats}): at short from-scratch budgets, preprocessing defaults and
initialization variance dominate, and only a fully-matched recipe isolates the
effect of the training loop --- which is, as expected, negligible.

\subsection{E5: Deployment (quantization)}
\label{sec:e5}
We report model size and single-image CPU inference latency for FP32, dynamic
INT8, and static (FX graph-mode) INT8 post-training quantization on a ResNet-18
at $224{\times}224$ (Table~\ref{tab:deploy}). Two findings are instructive and
honestly reported. First, \emph{dynamic} quantization only quantizes linear
layers and therefore yields negligible benefit on a convolution-dominated CNN;
it is appropriate for transformer/MLP-heavy models. Second, \emph{static} FX
quantization requires a symbolically traceable model: it delivers a
$3.96\times$ size reduction and $2.4\times$ speedup on a standard torchvision
ResNet-18, but FujiCV's assembled model (a \texttt{timm} backbone behind a
wrapper) is not always FX-traceable, so static PTQ should be applied to a
traceable backbone or via the ONNX quantization path. This is a current
limitation (\S\ref{sec:conclusion}).

\section{Threats to Validity}
\label{sec:threats}
\textbf{Fairness of throughput comparisons.} Throughput measurements are only
meaningful when the compared pipelines perform identical work. In an early
iteration of E2 the hand-written baseline omitted the per-epoch validation pass
and metric collection that FujiCV performs by default, producing a misleading
apparent overhead of $+55\%$; equalizing functionality (train, validate, track
train/validation accuracy, checkpoint) reduced this to $+4.1\%$, within the
run-to-run standard deviation. We therefore report mean\,$\pm$\,std over three
runs after a warmup, on a quiescent machine, and equalize functionality
explicitly. Absolute throughput remains sensitive to data-loading, worker count,
and machine contention.

\textbf{Fairness of accuracy comparisons.} Accuracy parity (E3) is only
meaningful when the model, augmentation, and preprocessing are identical.
Removing three confounds --- augmentation strength, backbone implementation
(timm vs.\ torchvision), and the validation transform --- moved the apparent gap
from nearly six points to $+1.0$~pt, within variance. At short from-scratch
budgets, initialization variance and preprocessing defaults dominate; a
fully-matched recipe (and, ideally, multiple seeds or a pretrained longer
schedule) is required to isolate the training loop.

\textbf{Nature of the contribution.} Several components wrap established
libraries (\texttt{timm}, \texttt{albumentations}, Hugging~Face). The
contribution is a \emph{standardized, tested, and unified integration} with
broad task coverage, not new learning algorithms; we do not claim
state-of-the-art accuracy.

\textbf{Lines of code} is an imperfect proxy for developer effort; we report it
under a fixed counting rule (non-comment, non-blank, non-docstring lines) for an
identically-specified pipeline, and release all three scripts.

\textbf{Hardware scope.} DDP correctness and the throughput/memory study were
validated on a single node; multi-node scaling is future work.
